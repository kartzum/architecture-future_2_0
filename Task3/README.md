## Разработка технологического радара и роадмапа изменений для поддержки бизнес-целей компании

### Технический радар

**ADOPT (активно используем и развиваем)**

Языки и фреймворки

* Python — основной язык для Data Science и ML. Бизнес-сценарии: разработка ИИ-моделей для диагностики, прототипирование аналитики, интеграция с ИИ-сервисами.
* Golang — язык для масштабируемых backend-сервисов. Сценарии: высокопроизводительные финтех-сервисы (транзакции, кредиты), надёжные интеграционные микросервисы.
* Java — стабильный язык для ядра финтех-систем. Сценарии: критичные банковские системы (РКО, кредитные договоры).

Инструменты

* API Gateway — шлюз для маршрутизации, безопасности и мониторинга. Сценарии: единая точка доступа для партнёров, управление трафиком и аутентификацией.
* IAM — централизованное управление идентификацией и доступом. Сценарии: разграничение доступа к медицинским и финансовым данным, аудит для регуляторов.
* ELK — система сбора и хранения журналов аудита. Сценарии: расследование инцидентов, отчётность для регуляторов.

Платформы и операции

* Облачная инфраструктура — базовый слой эластичной инфраструктуры. Сценарии: масштабирование под пиковые нагрузки, быстрый запуск новых направлений.
* Управляемые Kubernetes сервисы — платформа контейнерной оркестрации. Сценарии: оркестрация микросервисов, автоматическое масштабирование.

Практики и паттерны

* Геораспределённое развёртывание — архитектурный паттерн высокой доступности. Сценарии: непрерывность сервисов, локализация данных.
* REST/gRPC — стили коммуникации микросервисов. Сценарии: синхронное взаимодействие сервисов, низколатентный обмен.

**TRIAL (пилотируем и ограниченно внедряем)**

Инструменты

* Apache Spark — фреймворк распределённой обработки данных. Сценарии: пакетная обработка больших данных, подготовка данных для ИИ-моделей.
* Power BI (или аналог) — основной инструмент визуализации и BI. Сценарии: миграция существующих отчётов, создание дашбордов для руководителей.
* Apache Airflow — платформа управления workflow. Сценарии: оркестрация ETL/ELT-пайплайнов, мониторинг задач.
* GitLab CI / GitHub Actions / Jenkins — инструменты CI/CD. Сценарии: автоматизация тестирования и доставки обновлений.
* Docker — платформа контейнеризации. Сценарии: контейнеризация приложений для единообразного запуска.

Платформы и операции

* Data Lakehouse — объединяет преимущества Data Lake и Data Warehouse. Сценарии: единое хранение сырых и структурированных данных (медицинские исследования, транзакции, логи).
* Облачное хранилище данных (Snowflake, BigQuery, Redshift) — целевая платформа для аналитических нагрузок. Сценарии: высокопроизводительная аналитика по терабайтам данных, быстрые сложные отчёты.
* Kafka / Confluent Cloud — платформа потоковых данных. Сценарии: поставка событий в реальном времени, стриминг данных с устройств.
* Облачная ESB / iPaaS — управляемая интеграционная платформа. Сценарии: упрощение интеграции с партнёрами, снижение затрат на поддержку шины.

Практики и паттерны

* Data Mesh архитектура — организационный и архитектурный паттерн. Сценарии: децентрализация управления данными, ускорение вывода отчётов.
* Self‑service BI платформы — концепция и инструменты для бизнес-пользователей. Сценарии: портал самообслуживания для самостоятельной аналитики.
* Инфраструктура как код (Terraform) — практика управления инфраструктурой через код. Сценарии: быстрое развёртывание сред, автоматическое восстановление.

**ASSESS (изучаем и оцениваем)**

Инструменты

* Data Catalog — инструмент управления метаданными. Сценарии: ускорение поиска данных аналитиками, управление метаданными.
* Data Quality инструменты — инструменты профайлинга и тестирования данных. Сценарии: автоматическая проверка качества данных на входе.
* Apache Flink — фреймворк стриминговой обработки. Сценарии: анализ потоков данных в реальном времени (фрод-мониторинг, аномалии).
* MLflow / Kubeflow — платформы для оркестрации ML-пайплайнов. Сценарии: управление жизненным циклом ML-моделей, MLOps.
* Feature Store — централизованное хранилище признаков. Сценарии: переиспользование признаков между моделями.
* Prometheus + Grafana — стек для сбора метрик и визуализации. Сценарии: мониторинг доступности сервисов, проактивное оповещение.
* OpenTelemetry — фреймворк для наблюдаемости. Сценарии: сквозная трассировка запросов в микросервисах.

Платформы и операции

* Managed SQL (Cloud SQL, RDS, Azure SQL) — управляемые реляционные БД. Сценарии: быстрое создание баз для новых сервисов без администрирования.
* NoSQL базы (MongoDB, Cassandra, DynamoDB) — масштабируемые нереляционные хранилища. Сценарии: хранение неструктурированных данных, высокоскоростной доступ.

Практики и паттерны

* Data Marketplace — паттерн организации доступа к данным как к продукту. Сценарии: внутренний магазин данных, повторное использование дата-продуктов.

**HOLD (сохраняем, но не развиваем — постепенно выводим)**

Инструменты

* Microsoft SQL Server 2008 — устаревшая СУБД, подлежит замене. Сценарии: централизованное хранение данных и выполнение бизнес-логики (в настоящее время).
* Power Builder — устаревший инструмент разработки desktop-приложений. Сценарии: интерфейс операторов клиник.
* Apache Camel — устаревшая шина данных. Сценарии: интеграция между DWH и сервисами.
* Power BI — устаревший подход к созданию отчётности. Сценарии: набор заказных отчётов для руководства.

Платформы и операции

* Существующий DWH (SQL Server 2008) — устаревшее централизованное хранилище. Сценарии: источник исторических данных на время миграции.

### Обоснование планируемых изменений

**Этап 1. Подготовка**

* Чёткие домены и границы данных → независимость подразделений.
* Пилот Data Lakehouse → проверка отказа от монолитного DWH и оценка реальной производительности.
* MVP портала → ранний фидбек и корректировка требований.

**Этап 2. Создание первых функций и настройка миграции**

* Kubernetes → масштабирование и упрощение развития.
* Kafka → быстрое подключение и доработка с минимальными издержками.
* Облако → возможность реализации всех указанных требований.

**Этап 3. Запуск портала**

* Реализация основных сценариев с соблюдением требований по безопасности.

**Этап 4. Запуск основных функций**

* Data Catalog → обеспечения качества данных.
* Масштабирование → возможность обеспечивать нефункциональные требования.
* Мониторинг и наблюдаемость → ускорение исправления ошибок.

**Этап 5. Полноценный запуск и сопровождение**

* Отключение legacy → снижение затрат на поддержку.
* Оптимизация → снижение затрат на ресурсы.
* Развитие портала → доведение системы до соответствия всем требованиям.
